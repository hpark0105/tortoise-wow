# Tortoise-WoW working agreements

## Purpose and ownership

- Personal, local Turtle 1.18.1 build 7272 server. Priorities: gameplay correctness, character persistence, stability, maintainability; LLM bots come after baseline gameplay validation.
- `origin` is the personal fork; `upstream` is Penqle/tortoise-wow. Work on `personal-server` unless the user selects another branch. Keep user changes such as `.idea/` out of unrelated commits.
- Follow the operator-global head/worker policy. Hosted Codex owns scope, user communication, source verification, tests and acceptance. A bounded local worker must not launch another model session.

## Retrieval and token discipline

- Stable retrieval repository/workspace: `tortoise-wow`. Use the existing park-retrieval PostgreSQL and CPU embedding services; do not start a separate embedding stack or put embeddings on the local worker's GPU.
- For substantial work: confirm registration/health, sync this repository, search with exactly this scope, retrieve bounded context/symbols, then verify cited current source and hashes. If unavailable, state the reason and use the smallest direct-read fallback.
- Start with 2–4 search results and the relevant functions. Avoid whole-repository dumps, repeated broad searches, full SQL dumps, generated assets and vendor code. Use exact IDs/table names for database investigations; retrieve only needed rows.
- Use one fresh, serialized `park-agent exec` assignment for an eligible bounded heavy subtask, with a versioned evidence card containing scope, allowed files, hashes, expected output, tests, edit permission and uncertainties. Only one editing worker per worktree. Independently inspect its diff and evidence.
- Never send `.env`, credentials, character/account data, raw logs, client archives, backups, or environment maps to retrieval or workers. Local evidence belongs under ignored `local/`.
- Track new source before indexing. After changes/tests/diff review, sync this repository and report embedding/derived-write counts. Do not claim token savings without measurement.

## Build and runtime

- Read `docker/README.md` and `CONTRIBUTING.md` for relevant work. The README's explicit client/hotfix requirement takes precedence over older general contribution notes.
- Preserve `-DALLOW_TURTLE_ADDONS=ON`. Use matching extractors and verify all 158 DBC hashes. Keep collision and pathfinding enabled.
- Normal build: `docker compose build world`. Reuse the same `BUILD_JOBS` argument on incremental builds to preserve Docker caching. Resource limits are intentionally unset until real gameplay usage is measured.
- `docker compose up -d` starts the personal server. It is bound to localhost ports 3724 and 8085. Database credentials are in ignored `.env`; configurations are generated by `docker/server.py`.
- Accounts/characters live in the `tortoise-local_database` volume. Never delete/reset/prune personal volumes or import test data into them. Use an explicitly separate Compose project for destructive fixtures and restore tests; verify its identity before cleanup.
- Back up before live migrations or updates. Avoid interrupting an online player; check session state and communicate maintenance. Existing user authorization governs deployment—do not invent an additional approval requirement.
- Client/data extraction directories, `local/`, and credentials stay ignored by Git and Docker builds. Do not replace or re-extract validated client assets for unrelated code fixes.

## Validation

- Python/scripts: `python -m unittest discover -s docker -p 'test_*.py'`, `python -m py_compile docker/server.py`, PowerShell parser checks for changed `.ps1`, `bash -n` for changed shell scripts, `docker compose config --quiet`, and `git diff --check` as relevant.
- C++ changes: compile the server; test changed behavior against disposable database/world fixtures when it depends on startup or database content. A clean build alone does not prove gameplay correctness.
- Backups: `./docker/backup.ps1`; disposable restore smoke check: `./docker/test-restore.ps1`. Those smoke checks validate schema/baseline content, not exact character identity or state. Persistence claims require comparing saved character/inventory/quest state across an actual restart or restore.
- Gameplay claims need in-game evidence for the affected behavior: combat/XP, loot/equipment, quest completion, travel, death/recovery, and relogged state. Distinguish user observations, database evidence, log checks and untested behavior.
- Use versioned SQL migrations for confirmed data repairs; do not edit already-applied migrations, invent loot/destinations, or clear meaningful script bindings just to silence warnings. Upstream proposals use `sql/wip_updates/`; deliberate personal runtime migrations go in the ordered updater directory with provenance and isolated validation.
- Keep CI client-free. Game archives and private character backups must never be uploaded as CI artifacts.
