# Independent implementation review — 2026-09-11

Decision: **revisions required before accepting the implemented bot stories or
advancing to earned-state persistence and larger cohorts**. Reviewed the completed,
uncommitted local implementation on `personal-server`, based on HEAD `8a7f25a`.
This review does not deploy code or change Jira status.

There is useful progress: explicit ownership metadata, guarded persistent saves,
login generation tracking, timer/null fixes, bounded processing histograms, and
disposable integration fixtures. Compilation and happy-path tests are insufficient
to accept the failure-path and gameplay requirements below.

## Findings

1. **P1 — Temporary/custom bot login paths regress.** In
   `src/game/PlayerBots/PlayerBotMgr.cpp:402`, a fresh temporary entry starts in
   LOADING, then the new guard at line 412 rejects every non-OFFLINE entry.
   A newly constructed custom bot also fails the owner query at line 419 because
   its character is created later by its AI. The custom overload at lines 367–378
   returns true even when the delegated login fails. Separate these paths from
   persistent roster validation without weakening ownership or no-save guards.
   Evidence: current-source control flow; these overloads were not runtime-tested
   in this review.

2. **P1 — Provisioning reuses an orphan's account identity.**
   `PlayerBotMgr.cpp:601–623` considers real accounts and ownership bindings,
   but ignores reserved owners already present in `characters` without a binding.
   A disposable runtime reproduction seeded `Revieworphan` under account
   1000000000, then provisioned `Reviewfresh`. Both ended up with account
   1000000000. This violates distinct session identity and obstructs later orphan
   completion under the unique ownership-account constraint.

3. **P1 — An incomplete, inconsistent binding does not fail closed.**
   `PlayerBotMgr.cpp:727` validates an existing binding only when a roster row
   also exists. The runtime reproduction seeded character owner 1000000020 with
   binding 1000000021 and no roster row. Provisioning changed its roster count
   from zero to one. Loader quarantine afterward does not undo that mutation.
   Validate every existing binding before any write, regardless of roster state.
   Also check database write/commit results before reporting success. Character
   insertion at line 690 is outside the later binding/roster transaction, contrary
   to the progress entry's claim that creation is one transaction.

4. **P2 — Production provisioning departs from TW-010's native creation plan.**
   `PlayerBotMgr.cpp:687–699` inserts a minimally populated level-10 character
   directly, using synthetic account/GUID bands and no account row. It bypasses
   native account/character creation, including normal starting inventory and
   action setup. Loading repairs some state and learns default spells; that does
   not establish equivalence to normal creation. The new persistence contract
   changes the earlier design. Resolve that design departure explicitly, then
   use native creation or constrain this implementation to a disposable fixture.
   Row existence and successful login do not prove normal gameplay initialization.

5. **P2 — Tests do not exercise several claimed acceptance conditions.**
   `docker/test_bot_login_lifecycle.py:230` checks that normal cycling produces
   no stale-callback messages; it never delivers an old generation after retry.
   Its overlap check observes logs without issuing duplicate login requests.
   `docker/test_bot_save_guard.py:216` quarantines a human-owned roster row
   before login; it does not exercise an ephemeral session or ownership change
   at save time. Logout timestamps do not prove earned XP, inventory or quest
   persistence. Add direct failure-path tests; retain TW-011's actual restart
   and restore proof as a separate gate.

6. **P2 — Telemetry emission can block the world thread.**
   `src/mangosd/WorldRunnable.cpp:107–116` reports from the world thread through
   `PerformanceMonitor.cpp:262` and synchronous `sLog.outInfo`. The logger in
   `src/shared/Log.cpp:591–617` takes its shared lock and flushes stdout/file
   output. A blocked consumer can stall the world, violating TW-003's unavailable
   consumer criterion. Reporting cost is also outside the recorded duration.
   Use bounded asynchronous emission with a drop policy, or explicitly revise
   the requirement. Configuration tests and histogram self-tests do not prove
   consumer-failure safety. This finding is source-backed, not a blocked-pipe
   runtime measurement.

with R1; do not combine all fixes into one local-model prompt.

```gherkin

  Scenario: R1 - Reserve orphan identities (TW-010 / KAP-553)
    Given an orphan bot character owns a reserved account without a binding
    When another bot is provisioned and the orphan is subsequently resumed

    And a repeated provisioning request changes neither identity

  Scenario: R2 - Reject every inconsistent partial binding (TW-010 / KAP-553)

    And the result reports rejection rather than successful provisioning

    Given a persistent bot, a temporary existing-character bot and a custom AI bot

    Then each follows its intended creation and ownership rules

    And a failed login returns failure to its caller
    And ephemeral bots retain their no-save protection

    Given an ephemeral bot or persistent bot whose ownership has changed
    When its session attempts to save
    Then character ownership and gameplay state remain unchanged

  Scenario: R6 - Keep telemetry consumer failure off the world thread (TW-003)
    Given telemetry is enabled and its output consumer is deliberately blocked
    When reports are produced beyond the bounded output capacity
    Then world updates continue and queued telemetry remains bounded
```
