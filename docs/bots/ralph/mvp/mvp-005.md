Implementation notes (src/game/PlayerBots/PlayerBotAI.*):

- The combat loop now holds its target by GUID between the 2s combat ticks
  (in-combat victim fight, alive held-target chase/attack within 35yd, idle
  SelectNearestTarget(30) acquisition). Previously re-selection via
  SelectNearestTarget dropped the target mid-fight after the first out-of-range
  Attack. `TryLootDefeatedTarget` no longer clears the held target on an alive
  branch; loot of the dead target still happens at the top of UpdateAI.
- Idle wander is suppressed while a held target or a 30yd hostile exists, so
  wander cannot overwrite the chase.
- PLAYERBOT_DEBUG=1 observability: alive/dead transitions, 10s state heartbeat,
  per-tick fight/pursue/engage lines, and loot denial/slot diagnostics.

Fixture root cause (why the earlier lab looted 0 items):

- Fresh lab DBs import sql/base only; the base dump ships an EMPTY legacy
  `tw_world.migrations` table (no Module column), so at world start the C++
  DB Auto-Updater (AutoUpdater.cpp) replayed all 149 sql/database_updates
  files, and 20260510092659_world.sql's `REPLACE INTO creature_template`
  reset entry 6 `loot_id` to 6 before ObjectMgr loaded reference data.
- Fix: `docker/init-db-updates.sh` (mounted as
  /docker-entrypoint-initdb.d/20-apply-database-updates.sh in lab and personal
  compose) applies the ordered update files at db init and records each file's
  SHA-1 in the per-database `migrations` table, mirroring AutoUpdater.cpp
  (including the legacy-table Module ALTER and UPPERCASE hashes - the C++
  ByteArrayToHexStr is uppercase and key lookup is case-sensitive). The world
  auto-updater then finds nothing pending (the loot test asserts
  "[DB Auto-Updater] Attempting to execute update" is absent), and fixture
  seeds applied after db boot survive world load.
- A failed update makes mangosd block on stdin (AutoUpdater.cpp
  std::getline(std::cin)); a hung world is the failure symptom, not a crash.
